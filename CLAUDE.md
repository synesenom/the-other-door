# door — Claude Code guide

## Project goal

Automated job hunting pipeline: scrape job boards → score against a candidate profile → generate tailored application materials → (eventually) submit applications.

## Reporting back

When summarising what you just did, use at most 10 short bullet points: what happened, no details. Go into details only when asked.

## Conventions

- LinkedIn, profession.hu, HelloWork and Jobbsafari are employer discovery sources, not `Site`s (`core/discovery_sources.SOURCES`). All are logged out only (no login, cookies or session, guarded by `tests/core/test_no_forbidden_hosts_unit.py`), paced (LinkedIn 2-4 s, profession.hu 3-6 s), capped, stopped for the run on any pushback and rested for 24 h after a refusal (`pushback_at` in `jobs/discovery/<source>.json`).
- Terms verdicts (#569, docs/job-sites.md "How The other door fetches"): every source has one verdict, `allowed`, `unsure` or `reserved`: `Site.verdict` and `Site.terms_summary` (required), a discovery module's `VERDICT`, `TERMS_URL` and `TERMS_SUMMARY` (read through `discovery_sources.info`), and a "Terms" passage in its docstring quoting what it rests on. `unsure` = the terms forbid automated access on the host read (no terms found and unclear are `allowed`): it runs only once the user turned it on (the four discovery sources, each with its `<source>_discovery` key; `tests/core/test_sites_unit.py` refuses an `unsure` `Site` without a switch), and `core/disclaimer.py` is the one text shown when one goes on (`init`, `init --set`, `_init_core`'s `disclaimers`, the app's wizard and Profile; `doctor` and the run record's `unsure_on` list the ones on). `reserved` is never fetched. The fetch settings (`http_client.OBEY_ROBOTS`, `USER_AGENT`) are pinned by `tests/core/test_robots_guard_unit.py`.
- Discovery sources (#280): `discover` (`pipeline/discover.py`) runs every source in `core/discovery_sources.SOURCES` (name to dotted module) that the profile enables, one after the other on one worker thread. A source module (in `scrapers/discovery/`, importing `door` only through `scrapers/sdk.py`, scanned by `tests/scrapers/test_scraper_imports_unit.py`) has `NAME`, `COUNTRIES` (lowercase ISO codes, `()` = anywhere; `discovery_sources.selected` skips it as `not for <cc>`), `CONFIG_KEY` (a `<source>_discovery` bool, default false, declared in `Profile`; never set = `<key> not chosen`, false = `<key> is off`; `init`, `/onboard` and the app's onboarding ask about each source serving the city in their review, off unless ticked, `discovery_sources.for_location`, and `show_profile`'s `discovery_unchosen` names the ones never chosen, a line at the app sidebar's foot), `run(config, **kwargs) -> sdk.DiscoveryResult` and the optional hooks `enabled`, `extras(queue)` (more `run` kwargs) and `skip_employer(emp, state, now)` (a reason not to queue; the engine remembers it in the state's `seen`). Each source has its own state `jobs/discovery/<source>.json` (an older `jobs/linkedin_discovery.json` is copied there on load, never deleted), pace, rest and `record_error`/`record_pushback` bookkeeping under its `NAME`; the `discover` block keeps its flat fields (sums) and adds `sources`. The `li_*` progress stages are the generic ones of every source. A second source is a module, a `SOURCES` line, its key in `Profile` and its docs, with no change to `discover.py`.
- LinkedIn, the first source, is employer discovery, not a job source: `discover` has `linkedin.discover_run` (the source's `run`) read search cards over plain HTTP (one quoted query per keyword in `rotate` mode, the default, each paged newest first through the last 7 days; the combined `"a" OR "b"` form returns fewer cards) within a per-run request budget (150), 2-4 s between requests, one 429 waited out for 90 s and retried, and puts each employer in the candidates queue; `follow` (`pipeline/follow.py`) tries a LinkedIn employer by name first and finds the feed, and only the employers it could not resolve (`name_tried`) get a job page read by a later discover. A full `find` starts discover first on a worker thread (`discover.begin()`: network only, no `jobs/` writes; `Discovery.finish()` on the run's thread writes the queue and state) and runs a late follow/collect (`late=True` cores) for what it queued after those steps ran; `discover` alone is foreground. State: `jobs/discovery/linkedin.json` (`core/discovery_state.py`, `load(jobs_dir, source)`: `last_run`, `pushback_at`, `seen` Easy Apply employers retried after 90 days, `pace` budget/factor halved/doubled after a refusal and recovered after three clean runs, `history` of the last 30 runs with their first 429, `mode`/`rotation`/`searched`). The step runs on every full run once the user turned it on (`linkedin_discovery`, default false; skipped without keywords or while resting); a failure there never fails the run. Tests default the key to false (`tests/profile_utils.base_config`), refuse a real browser (`tests/commands/conftest.py`, `tests/pipeline/conftest.py`) and any real HTTP request (`tests/conftest.py`).
- Feed platforms (#282): each feed site's module detects its own feed (`detect_url`, `feed_url`, optionally `detect_cname`, `detect_html`, `name_probes`, `FEED_KEY`; platforms The other door knows but does not follow are detect-only modules `hr_on` and `phenom`, which can return `unfollowable(..., refusal="must_not"|"cant_yet")`; a module may add a `resolve(session, det, url)` look-through or a `follow_link(session, url)` hook, as `phenom` and `career_sites` do for a Workday site behind Phenom), `core/ats_detect.py` only dispatches over `PRECEDENCE`, `commands/companies.py` holds no feed endpoint; `tests/scrapers/test_feed_contract_unit.py` checks it. An employer no link or name probe resolves is looked up by name on Wikidata (#566, `core/wikidata.py`: the public API, no key; its name trimmed of legal forms and `subsidiary_words`, the organisation in the profile's country first, its official website and its parent's; at most 60 names a run, a 429 or 5xx is waited out once, `Retry-After` capped at 60 s, every lookup waiting with it, and only a second refusal stops it for the run; an employer it was not asked about, stopped or budget spent, stays queued, not recorded as unresolved) and `companies._by_website` reads that website, the careers hosts of its domain and each module's optional `tenant_probe(session, slug)` (Workday); tests get no answer from it unless they serve the saved ones (`tests/conftest.py` `_no_wikidata`, `tests/wikidata_utils.py`).
- Scraper SDK: `src/door/scrapers/sdk.py` is the one module a site scraper imports `door` code from (re-exports of `door.scrapers` plus named wrappers that call `title_fit`, `locality`, `ats_detect`, `i18n`, `freshness` through their modules); `tests/scrapers/test_scraper_imports_unit.py` fails on any other `door` import in a `SITES` module, nested ones included (`linkedin.py` is not a `Site` and is exempt until #280). `_scrape_core` puts runtime keys in the config, `_mode`, `_country` (lowercase ISO code or `None`; read with `sdk.country(config, served)`) and, when collecting, `_names` (`{config_key: {companies.entry_key(entry): followed name}}`; a single-employer feed scraper names its postings with `sdk.followed_name(config, key, raw_entry, fallback)`, its own guess only the fallback, guarded by `tests/scrapers/test_feed_contract_unit.py`; `hr_manager` and Workable's search keep their own names), not declared in `Profile`; a board with a country fallback keeps `_SERVED` (`thehub`), pinned to the registry by a test.
- Scrapers are stateless functions — they accept the profile `config` dict and return structured data (`JobPosting` dicts); no side effects.
- All personal data (CV, config) lives under `profile/` and is gitignored (except LaTeX templates). Never commit real CV content.
- Job postings are stored as JSON: `{id, title, company, location, url, description, posted_at, source}`, plus an optional `employer` (the `profile/companies.json` entry it belongs to: `collect` stamps it, `search` only on a name or alias match). The job id is `<site>.<platform_id>` (`models.make_job_id(site, platform_id)`; the platform id is normalised, and SuccessFactors, Teamtailor and Pinpoint fold the employer's host in with `models.tenant_platform_id`); `jobs/history.json`, the ledger and `jobs/output/` use the same key (`known_ids` still hands scrapers raw platform ids). `scripts/migrate_job_ids.py [--dry-run]` converts older data once.
- Scores are attached at match time and written back to the same JSON — there is no separate `matched/` tree; scored postings live at the same path as raw postings.
- Raw and scored postings: `jobs/postings/<YYYY-MM-DD>/<site>/<job_id>.json`
- Generated materials: `jobs/output/<job_id>/cv.tex`, `cover_letter.tex`, and compiled PDFs, plus `facts.json` (`tailoring/facts.py`, run by the tailor itself through the `check_facts` tool, two rounds a prepare run, and again by `prepare` and `revise`; an item still flagged keeps the `reason` the tailor recorded for it, never a TODO, and a company form is no skill: the numbers, years, employers, skills and tools, certifications and degrees not found in `profile/cv.md` or the story bank (`kind`: `number`, `year`, `employer`, `skill`, `certification`, `degree`, and `placeholder` for a `TODO`, a gap of `cv.md`'s, always flagged; - The app shows an error only when it keeps the user from a mistake or they can fix it themselves; a failure the app retries or the user cannot act on is said nowhere (`docs/design/README.md`, principle 9).
- No backward compatibility while in development: a removed or renamed command, option or
  config key is deleted everywhere (code, tool, docs, tests) as if it never existed. No aliases,
  no "X was renamed / is no longer a setting" messages, no code that drops old keys, no doc
  sentence saying something is gone. A user `profile/config.json` that uses a removed key is
  fixed directly.

## Code layout rules

- A command lives in `src/door/commands/<name>.py`: its `_<name>_core` (side effects, returns
  a dict, never prints) and the Click command that renders it, registered in `src/door/cli.py`.
  The top-level help is sectioned (`_SECTIONS` in `cli.py`: Set up, Find, Your lists, Your CV, Move); a new top-level command goes into one.
  What several commands share goes in `src/door/commands/_common.py`. `find` is five steps, one
  module each under `src/door/pipeline/` (`search.py`, `discover.py`, `follow.py`, `collect.py`,
  `match.py`; each core returns its block of the run record and never prints) composed by
  `_find_core` in `commands/find.py`. They share the engine `_scrape_core` in `commands/scrape.py`
  (`search` and `collect` call it with their own site list and mode; its `_scrape_passes`
  are run once by the match step) and `_match_core` in `commands/match.py` (scoring).
- Call into another module through the module, never a name imported from it:
  `from door.commands import scrape as scrape_cmd` then `scrape_cmd._scrape_core(...)`, and
  `workspace.JOBS_DIR` (from `door.core import workspace`), read at call time. Tests patch
  the module that defines a name (`monkeypatch.setattr(scrape_cmd, "_scrape_core", ...)`,
  `monkeypatch.setattr(workspace, "JOBS_DIR", tmp)`), and that only reaches every caller
  when callers look the name up on that module.
- The CLI prints a path under the repo relative to it (`common._display_path`: `jobs/output/<id>/cv.pdf`),
  any other path whole; cores and MCP tools return absolute paths (Claude reads the files).
- `src/door/__init__.py` re-exports nothing, so a patch aimed at `door.<name>` fails loudly
  instead of silently patching nothing.

## Running tasks

Stack: **Python 3.12**, dependencies managed with **Poetry only** (`package-mode
= false` — the repo runs in-place, it is not built or installed as a package). The
package lives in `src/door/`; whatever runs it puts `src/` on `PYTHONPATH` — the root
`./door` script (`door.cmd` on Windows), `.mcp.json`'s `env`, pytest's `pythonpath`.
`./door <command>` is the only CLI spelling; `poetry run python -m door` from the
root no longer finds the package.

```bash
poetry install                                 # set up the environment

./door find                # five steps: search the boards, discover employers (LinkedIn), follow
                            # their feeds, collect them, match (filter + score with Haiku), summarise
./door find --skip discover,collect   # leave steps out (options of the group go before a step name)
./door find --boards jobindex,thehub  # search only these boards
# the single steps are hidden from --help (users only see `find`), kept for debugging one step:
./door find follow --dry-run          # what `follow` would record in profile/companies.json
./door find collect --company Trustpilot   # just that followed employer
./door find match          # score what is unscored, list the matches at min_score
./door jobs               # the matches you haven't acted on, best first (--new, --score X)
./door jobs show trustpilot   # one posting in full, named by company/title words (several: pick; none: pick from all); `jobs add URL|TEXT`, `jobs status` (pick a job and a status from lists), `jobs summary` (the dashboard), `jobs prepare trustpilot`
./door cv enrich <url ...>   # propose CV additions from public pages, then add the ones you pick
./door cv gaps --job trustpilot   # skill-gap report + learning plan for a posting (or role names, or --top N)
./door doctor             # prerequisites check (LaTeX, claude, MCP entry); --probe adds live site probes
./door doctor --fix       # install Tectonic/claude if missing (asks once), check the MCP server
./door data export        # pack profile/ and jobs/ to move computers (`data import` on the other one)
./door companies add Trustpilot   # detect a company's feed and follow it (`--dry-run` shows it first); `companies` lists, `remove`, `why`

./scripts/run-test.sh           # offline tests + coverage + badge (see Testing)
./scripts/run-test.sh --live    # opt-in live smoke tests
```

### MCP server

Every CLI command is also an MCP tool (`src/door/mcp_server.py`), so an LLM client can drive
the pipeline with typed tool calls instead of shelling out and parsing stdout. Each tool
wraps the same `_*_core` function its Click command calls (`src/door/commands/<name>.py`: `_find_core` (the `find_jobs` tool: `step`, `skip`, `boards`, `company`, `dry_run`, ...), `_list_core` (`jobs`),
`_prepare_core`, `_doctor_core`, …) — no behaviour is duplicated between the two
surfaces. Cores return dicts and never print; expected failures come back from a tool as
`{"error": ...}`.

```bash
PYTHONPATH=src poetry run python -m door.mcp_server   # run the server directly (stdio transport)
```

An in-repo `.mcp.json` registers the server for Claude Code (auto-connects when this
repo is opened — see `/mcp`); other MCP clients can point their own config at the same
`command`/`args`. **Adding a CLI command means adding its tool too:** map it in
`CLI_COMMAND_TOOLS` (`src/door/mcp_server.py`); `tests/commands/test_mcp_server.py` fails until the
tool list equals the command list, and until the tool takes every option the command takes
(and vice versa) — `--quiet` excepted; a renaming goes in that test's `_ALIASES`.
A tool with no command is allowed only by name in `CONVERSATION_ONLY_TOOLS` (`revise`,
`mark_reviewed`, `mark_seen`, `compile`, `check_facts`, `preview_matches`: what a user says to Claude, or an agent's or a wizard's plumbing). The CLI is
two levels where it helps: `cv enrich|gaps|titles|stories` (`cv stories list|add|remove|draft`, bare = list), `companies list|add|remove|why`, `jobs list|show|add|status|summary|prepare` (bare `jobs` is `jobs list`), `data export|import` and `find search|discover|follow|collect|match` (keys like `"data export"`
in `CLI_COMMAND_TOOLS`; the five `find` steps are one `find_jobs` tool whose `step` parameter picks the subcommand, with the group's own options like `skip` beside it); `doctor --fix` is the `setup` tool. Skills and agents call these tools — no `.claude/` file
runs `./door`. See
`docs/architecture.md`'s "Two modes, one core" section for the full CLI / MCP /
skills-and-agents model; the tool table users read is `docs/manual-claude.md`.

### Review sessions (default behaviour of a conversation in this repo)

The user runs door by hand when they sit down; a conversation here fetches what's new
and helps decide. Unless the user asks for something else:

1. Start with `status_summary` — its `since_last_review` block says how many runs
   happened, how many new matches cleared `min_score`, and which sites failed. Mention
   failures briefly; don't try to fix them unasked. If there has been no run since the
   last review (or the user asks for fresh jobs), offer to call `find_jobs` — it scrapes only
   postings published since each site's last scrape, then scores them (minutes).
   Its `plan` block says how full the Claude plan is: mention it only when it has a `warning`
   or little room; answer "can I prepare three more?" or "why did I hit my limit?" from it
   (`room`, `week`), saying it is an estimate as of `as_of`.
2. Then `list_matches(new_only=True)` (or plain `list_matches` if nothing is new, or the
   user wants everything). Present postings by title and company (with `title_en` next to
   a title in another language), never with numbers. The user names a job in their own
   words ("the Trustpilot one"); pass the `id` from the list you showed, or their words —
   every tool that takes a `job_id` accepts words from the company and title, and returns
   `candidates` when several jobs match: ask which with AskUserQuestion. Never ask the user
   for a job id or a path.
3. Don't call `find_jobs` (it re-scrapes and re-scores) without the user's go-ahead.
   If a tool says
   "a run is in progress", tell the user and wait — don't retry in a loop.
4. "show the Trustpilot one" → `show`; "not this one" → `set_status` `discarded` (their reason in `notes`); "prepare it" →
   `prepare` ("prepare the best one": no `job_id`), then `show` and summarise its `materials` (keywords, what was tailored, page counts, letter length) with
   the PDF paths; `materials.unsupported` lists numbers, years, employers, skills, certifications and degrees in the CV or letter that `cv.md` and the story bank do not back, each with its context line: tell the user and offer `revise` to remove or fix them (never edit the `.tex`); `[]` is clean, `null` means not checked (no `cv.md`), and a sent status's `warning` may list them too; `materials.readability` lists what an ATS would not read back from the PDFs (`tailoring/readability.py`, pypdfium2 text: name, headings on their own line and in order, keywords, garbled or empty text; `[{file, kind, detail}]`, `[]` clean, `null` not checked): tell the user and offer `revise`; "tighten …" → `revise` (then `show` again); "undo" → `revise(undo=True)`.
   Change a prepared `.tex` only through `revise`, never with Write/Edit: `revise` recompiles
   and re-renders, so the PDF never goes stale (there is no compile command for the user);
   "applied" → `set_status`; an interview → `set_status` `interview:<kind>` (screening,
   impression, assessment, technical), one call per round (if the user doesn't say which kind, ask
   with AskUserQuestion, the four as options; "rejected" ends the last round); never ask the user
   to type a status, a kind or a job id from memory — offer the list; "here's a link" → `import_posting` with only the `url` (it fetches the page and Haiku reads title and company; if that errors, ask for the text); "here's an ad I found" → `import_posting` with the pasted
   text (ask for title/company if the ad doesn't make them clear); either way it is scored at once —
   give its score and reason and let the user decide (`prepare`, `discarded`, …).
5. When the user says they are done, call `mark_reviewed`.

## Testing

This project is developed **test-first (TDD)**. The cycle is non-negotiable for
new behaviour:

1. **Red** — write a failing test that pins the behaviour you want.
2. **Green** — write the minimum code to make it pass.
3. **Refactor** — clean up with the test as a safety net.

Practical rules:

- No new scraper logic (parsing, mapping, pagination, dedup) lands without a
  test written first. Bug fixes start with a failing test that reproduces the bug.
- Keep parsing **pure and separable** from network I/O so it can be tested
  without a live site — this is the main reason the helpers in each scraper
  (`_location_text`, `_parse_stash`, …) are standalone functions.
- Tests must be deterministic and offline by default. Anything that touches the
  network goes behind the `live` marker.
- Test behaviour, not decisions: no test that only asserts an option, command or
  field is gone, that `--help` lists exactly these options, or that an old name is
  rejected. When removing or renaming, update or delete the tests that break.
- While iterating on a change with the user (a live UI session), do not run the
  tests after each edit; run them once, before the PR.

### Layout

`tests/` mirrors the package (see `tests/README.md`): `scrapers/` holds each
scraper's tests next to its saved `fixtures/<site>/`; `commands/` has one
`test_<command>_cli.py` per CLI command (shared `cli_env` in `commands/conftest.py`,
helpers in `tests/cli_utils.py`); then `core/`, `matching/`, `tailoring/`. Use `tests/paths.py` (`REPO_ROOT`, `TESTS_DIR`,
`GOLDEN_DIR`) instead of `Path(__file__).parent...`.

### Three layers

| Layer | Scope | Network | Where |
|-------|-------|---------|-------|
| **Unit** | Pure helpers + `models.py` in isolation (`make_job_id`, `_location_text`, `_parse_date`, `_area_for_profile`, `_country_code`, date/URL fallbacks). | No | `tests/<area>/test_*_unit.py`, `tests/core/test_models.py` |
| **Fixture** | The whole `scrape(config)` path — pagination, dedup, raw→`JobPosting` mapping — with HTTP mocked (`responses`) from saved real payloads. | No (mocked) | `tests/scrapers/test_*_scrape.py` + `fixtures/<site>/` beside them |
| **Smoke** | Thin contract check against the *live* site: returns ≥1 valid `JobPosting` with non-empty `title`/`company`/`url`. Catches silent breakage when a site changes. The weekly CI run leaves out the discovery sources' live tests (`tests/scrapers/discovery/`), which run locally. Countries and ad languages are checked offline on saved real ads (#19: `tests/i18n/test_country_corpus.py`, `test_language_corpus.py` read `tests/i18n/corpus/`, which `scripts/refresh_corpus.py` writes from the rows in `tests/live_matrix.py`, the only part online; a row required per data file by `tests/i18n/test_live_matrix_unit.py`), and `scripts/smoke_report.py` lists boards, employer feeds and the matcher's golden cases separately on `docs/badges/live-smoke.md` (a list a run did not test keeps its last result: CI has no Claude plan and skips the golden set), with one README badge each (`docs/badges/live-<dimension>.svg`, "passed/total", green when all passed, red when one changed, orange otherwise). Three verdicts (#19, `tests/live_utils.py`): passed, changed (a failure: the only one that opens the failure issue) and not reached (a refusal or an unreachable host: `not_reached_if_refused(site, errors)` or `not_reached(site, why)` skip with `not reached:`, locally and in CI; the page counts the runs in a row, and 3 open an issue of their own). | Yes | `tests/**/test_*_live.py`, marked `@pytest.mark.live` |

Note: `scrape()` swallows network/parse errors (prints and returns `[]`) so a
single bad request never crashes a run — but it also calls `record_error()`
(`src/door/scrapers/__init__.py`) alongside every such print, so `_scrape_core`
can tell a genuinely quiet day apart from a broken scraper after the fact: a
site with `count == 0` and no recorded errors is `outcome: "ok"`; a site with
`count == 0` and recorded errors is `outcome: "failed"`, with the captured
messages under `"errors"` (a site with `count > 0` always stays `"ok"`, even
if some requests also failed — partial success isn't downgraded). A site that
returned not a single record — no errors, but nothing new, known or too old
either, and no recognised zero-hit results page (`sdk.record_answered`: a scraper that read the site's own "no hits" answer, which is a quiet day, `ok`) — is `outcome: "empty"` with a `"warning"`: a flag (the site may have
changed), not a failure — exit code unchanged, watermark not moved, and listed
in `status_summary`'s `site_failures`. A per-company feed platform that no followed
employer uses is never fetched (`collect` does not even list it unless named): `outcome: "not_configured"`, a quiet skip; a site resting
after pushback (`Site.cooldown_hours`) is skipped as `outcome: "resting"` with its `until`, also a quiet
skip. `find`
exits non-zero (2) if any site comes back `"failed"` or `"error"`. The smoke layer is
still what catches a *systemic* site change offline testing can't see — keep
it asserting ≥1 result.

### Commands

```bash
poetry install   # runtime + dev deps (pytest, pytest-cov, pytest-xdist, responses, genbadge)

./scripts/run-test.sh           # offline suite + coverage + regenerate badge
./scripts/run-test.sh --live    # opt-in smoke tests against real sites
./scripts/run-test.sh --skills  # the skills (/onboard) run by the real model on your plan, before a release
./scripts/run-test.sh --app     # the desktop app's tests as CI runs them (typecheck, unit, e2e, core journeys, phone)
./scripts/run-test.sh --release # before a release: offline suite, app with every journey, skills, and the
                                # install test when DOOR_INSTALLER names an installer; a PASS/FAIL line each
```

The skill tests (`tests/skills/`, marker `skills`, never in CI) run a Claude Code skill with the real
model through the Agent SDK (`claude-agent-sdk`, on the plan `claude` is signed in to, the API key cleared)
against the app's test world (`app/test/world/make-world.ts`: `boot.py`'s server, the stand-in `claude.py`
for the tools' own model calls), with a small model playing the persona (`tests/skills/skill_run.py`, which
also runs one skill by hand and writes its transcript). They check behaviour only: the tools and their order,
what was written and when. `tests/skills/test_skill_contract_unit.py` (offline) checks that every tool a skill
or agent names exists, with the parameters it passes.

The offline suite runs in parallel (`pytest -n auto`, pytest-xdist, in `run-test.sh` and CI;
`-n 0` runs it serially, and live runs stay serial), so a test must not share a fixed path,
port or global with another: use `tmp_path` and the `tests/conftest.py` fixtures.

### Coverage badge

Coverage is reported with `pytest-cov`/`coverage` (config in `pyproject.toml`)
and rendered into a badge **entirely locally** with `genbadge` — no Codecov or
other external service. The badge SVG lives at `docs/badges/coverage.svg` and is
committed so it shows in the README. Regenerate it by running `./scripts/run-test.sh`
after changing tests; `coverage.xml` and `.coverage` are gitignored, only the
SVG is tracked.

## Docs maintenance

README is only the get-started path plus links; reference material lives in `docs/`. When
an implementation adds user-facing behaviour, update the matching doc: a CLI command →
`docs/manual-cli.md` and `docs/manual-claude.md`; a config key → `docs/configuration.md`; a
scraper → `docs/job-sites.md` (and `docs/architecture.md`'s Scrapers table); a skill →
`docs/skills.md`; a change to how data is stored → `docs/how-it-works.md` or
`docs/architecture.md`. Touch README only when the get-started steps change. Do not update
docs for internal refactors, test additions, or changes with no user-visible effect.
