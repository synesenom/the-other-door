# door — Claude Code guide

## Project goal

Automated job hunting pipeline: scrape job boards → score against a candidate profile → generate tailored application materials → (eventually) submit applications.

## Reporting back

When summarising what you just did, use at most 10 short bullet points: what happened, no details. Go into details only when asked.

A pipeline (`/dev-resolve`, `/dev-epic`) never stops until its work is implemented (`/dev-epic`: every sub-issue implemented, every box checked). The only reason to stop and wait for the user is a decision the `decider` returned CANNOT DECIDE on. Finishing a step, an agent returning, an issue filed, a merge or a permission to wait for are not reasons to stop: go straight on to the next step. Anything else only the user can give (a permission the harness asks for, a merge, a FAIL after two attempts) blocks that one item, never the run: ask for it in one line and go on with every other item. After the user merges or grants something, re-read what it unblocked and start it in the same turn.

## Decisions

When a question comes up that is the user's to decide (a design choice, a policy, a trade-off, which option of several), do not ask it first. Spawn the `decider` agent (`.claude/agents/decider.md`, on Fable) with the question, the options you see and the context; it researches the codebase, the docs, the issues and PRs and the web, and returns one definite decision with its reasons, or CANNOT DECIDE. Act on a decision and name it, with its main reason, in your report. Ask the user (AskUserQuestion) only on CANNOT DECIDE, with the question as the agent put it and what it found.

This is for decisions, not permissions: a skill's or the harness's confirmation before an action that is hard to undo or outward-facing (pushing a tag, publishing a release, deleting data) is still asked of the user.

## Review

Before summarising a change you implemented (a PR, or a branch about to become one), spawn the reviewers in parallel, each with the base branch and the issue or goal:

- `gap-reviewer` (`.claude/agents/gap-reviewer.md`), always: what the change leaves missing (the goal not met, inconsistencies, untested cases, false docs, follow-ups).
- `simplicity-reviewer` (`.claude/agents/simplicity-reviewer.md`), always: complexity in the new lines (needless abstraction, dead code, old behaviour kept alive, a diff larger than its goal, simpler shapes).
- `design-reviewer` (`.claude/agents/design-reviewer.md`), when the change touches the app's screens (`app/src/renderer/`, `app/src/web/`, `app/src/preview/`) or `docs/design/`: the visual and UX rules of `docs/design/README.md`, checked on the rendered preview.

Then, once their findings are dealt with, spawn `integration-reviewer` (`.claude/agents/integration-reviewer.md`) last, on the final diff: it maps the change's blast radius and asks whether the whole solution would be smaller had the feature been in the codebase's founding principles, so the code does not grow by accretion.

Each reports its findings with evidence. Every finding, and every one you found yourself, ends in one of two ways before you summarise: fixed in the change (small and in scope, test-first like any change), or filed as a GitHub issue (larger, or out of scope) whose number you give. The summary names each finding and which way it went; none is only mentioned. A finding you judge not real: say why in one line.

## Pull requests

A PR you open (by `/dev-pr` or any other way) is yours until it is green: watch it and fix what breaks, without being asked.

- Watch its checks after every push (subscribe to its activity where the session can, else poll its check runs every few minutes) until every check has finished.
- A failing check: read its logs, find the cause, fix it test-first on the branch, push, and watch again. A flaky failure (passes on a rerun with no change) is rerun once and named in the report; one that fails again is a failure.
- A merge conflict with `main` (or `main` moving under it): merge `origin/main` into the branch, resolve the conflicts keeping both sides' intent, run the tests the conflicting files touch, push, and watch again.
- A git push the sandbox blocks (no keychain, no `~/.config/gh`) is retried with the sandbox off, not handed to the user.
- Stop only when every check is green and the branch merges cleanly; then report it in one line. A fix that needs a decision goes to the `decider` (see Decisions); escalate to the user only on CANNOT DECIDE, or after three rounds of fixes that did not turn it green, with what was tried.

## Conventions

- LinkedIn, profession.hu, HelloWork and Jobbsafari are employer discovery sources, not `Site`s (`core/discovery_sources.SOURCES`). All are logged out only (no login, cookies or session, guarded by `tests/core/test_no_forbidden_hosts_unit.py`), paced (LinkedIn 2-4 s, profession.hu 3-6 s), capped, stopped for the run on any pushback and rested for 24 h after a refusal (`pushback_at` in `jobs/discovery/<source>.json`).
- Terms verdicts (#569, docs/job-sites.md "How The other door fetches"): every source has one verdict, `allowed`, `unsure` or `reserved`: `Site.verdict` and `Site.terms_summary` (required), a discovery module's `VERDICT`, `TERMS_URL` and `TERMS_SUMMARY` (read through `discovery_sources.info`), and a "Terms" passage in its docstring quoting what it rests on. `unsure` = the terms forbid automated access on the host read (no terms found and unclear are `allowed`): it runs only once the user turned it on (the four discovery sources, each with its `<source>_discovery` key; `tests/core/test_sites_unit.py` refuses an `unsure` `Site` without a switch), and `core/disclaimer.py` is the one text shown when one goes on (`init`, `init --set`, `_init_core`'s `disclaimers`, the app's wizard and Profile; `doctor` and the run record's `unsure_on` list the ones on). `reserved` is never fetched. The fetch settings (`http_client.OBEY_ROBOTS`, `USER_AGENT`) are pinned by `tests/core/test_robots_guard_unit.py`.
- Discovery sources (#280): `discover` (`pipeline/discover.py`) runs every source in `core/discovery_sources.SOURCES` (name to dotted module) that the profile enables, one after the other on one worker thread. A source module (in `scrapers/discovery/`, importing `door` only through `scrapers/sdk.py`, scanned by `tests/scrapers/test_scraper_imports_unit.py`) has `NAME`, `COUNTRIES` (lowercase ISO codes, `()` = anywhere; `discovery_sources.selected` skips it as `not for <cc>`), `CONFIG_KEY` (a `<source>_discovery` bool, default false, declared in `Profile`; never set = `<key> not chosen`, false = `<key> is off`; `init`, `/onboard` and the app's onboarding ask about each source serving the city in their review, off unless ticked, `discovery_sources.for_location`, and `show_profile`'s `discovery_unchosen` names the ones never chosen, a line at the app sidebar's foot), `run(config, **kwargs) -> sdk.DiscoveryResult` and the optional hooks `enabled`, `extras(queue)` (more `run` kwargs) and `skip_employer(emp, state, now)` (a reason not to queue; the engine remembers it in the state's `seen`). Each source has its own state `jobs/discovery/<source>.json` (an older `jobs/linkedin_discovery.json` is copied there on load, never deleted), pace, rest and `record_error`/`record_pushback` bookkeeping under its `NAME`; the `discover` block keeps its flat fields (sums) and adds `sources`. The `li_*` progress stages are the generic ones of every source. A second source is a module, a `SOURCES` line, its key in `Profile` and its docs, with no change to `discover.py`.
- LinkedIn, the first source, is employer discovery, not a job source: `discover` has `linkedin.discover_run` (the source's `run`) read search cards over plain HTTP (one quoted query per keyword in `rotate` mode, the default, each paged newest first through the last 7 days; the combined `"a" OR "b"` form returns fewer cards) within a per-run request budget (150), 2-4 s between requests, one 429 waited out for 90 s and retried, and puts each employer in the candidates queue; `follow` (`pipeline/follow.py`) tries a LinkedIn employer by name first and finds the feed, and only the employers it could not resolve (`name_tried`) get a job page read by a later discover. A full `find` starts discover first on a worker thread (`discover.begin()`: network only, no `jobs/` writes; `Discovery.finish()` on the run's thread writes the queue and state) and runs a late follow/collect (`late=True` cores) for what it queued after those steps ran; `discover` alone is foreground. State: `jobs/discovery/linkedin.json` (`core/discovery_state.py`, `load(jobs_dir, source)`: `last_run`, `pushback_at`, `seen` Easy Apply employers retried after 90 days, `pace` budget/factor halved/doubled after a refusal and recovered after three clean runs, `history` of the last 30 runs with their first 429, `mode`/`rotation`/`searched`). The step runs on every full run once the user turned it on (`linkedin_discovery`, default false; skipped without keywords or while resting); a failure there never fails the run. Tests default the key to false (`tests/profile_utils.base_config`), refuse a real browser (`tests/commands/conftest.py`, `tests/pipeline/conftest.py`) and any real HTTP request (`tests/conftest.py`).
- Feed platforms (#282): each feed site's module detects its own feed (`detect_url`, `feed_url`, optionally `detect_cname`, `detect_html`, `name_probes`, `FEED_KEY`; platforms The other door knows but does not follow are detect-only modules `hr_on` and `phenom`, which can return `unfollowable(..., refusal="must_not"|"cant_yet")`; a module may add a `resolve(session, det, url)` look-through or a `follow_link(session, url)` hook, as `phenom` and `career_sites` do for a Workday site behind Phenom), `core/ats_detect.py` only dispatches over `PRECEDENCE`, `commands/companies.py` holds no feed endpoint; `tests/scrapers/test_feed_contract_unit.py` checks it. An employer no link or name probe resolves is looked up by name on Wikidata (#566, `core/wikidata.py`: the public API, no key; its name trimmed of legal forms and `subsidiary_words`, the organisation in the profile's country first, its official website and its parent's; at most 60 names a run, a 429 or 5xx is waited out once, `Retry-After` capped at 60 s, every lookup waiting with it, and only a second refusal stops it for the run; an employer it was not asked about, stopped or budget spent, stays queued, not recorded as unresolved) and `companies._by_website` reads that website, the careers hosts of its domain and each module's optional `tenant_probe(session, slug)` (Workday); tests get no answer from it unless they serve the saved ones (`tests/conftest.py` `_no_wikidata`, `tests/wikidata_utils.py`).
- Scraper SDK: `src/door/scrapers/sdk.py` is the one module a site scraper imports `door` code from (re-exports of `door.scrapers` plus named wrappers that call `title_fit`, `locality`, `ats_detect`, `i18n`, `freshness` through their modules); `tests/scrapers/test_scraper_imports_unit.py` fails on any other `door` import in a `SITES` module, nested ones included (`linkedin.py` is not a `Site` and is exempt until #280). `_scrape_core` puts runtime keys in the config, `_mode`, `_country` (lowercase ISO code or `None`; read with `sdk.country(config, served)`) and, when collecting, `_names` (`{config_key: {companies.entry_key(entry): followed name}}`; a single-employer feed scraper names its postings with `sdk.followed_name(config, key, raw_entry, fallback)`, its own guess only the fallback, guarded by `tests/scrapers/feeds/test_feed_names_contract.py`; `hr_manager` and Workable's search keep their own names), not declared in `Profile`; a board with a country fallback keeps `_SERVED` (`thehub`), pinned to the registry by a test.
- Scrapers are stateless functions — they accept the profile `config` dict and return structured data (`JobPosting` dicts); no side effects.
- All personal data (CV, config) lives under `profile/` and is gitignored (except the HTML templates and fonts in `profile.example/`). Never commit real CV content.
- Job postings are stored as JSON: `{id, title, company, location, url, description, posted_at, source}`, plus an optional `employer` (the `profile/companies.json` entry it belongs to: `collect` stamps it, `search` only on a name or alias match). The job id is `<site>.<platform_id>` (`models.make_job_id(site, platform_id)`; the platform id is normalised, and SuccessFactors, Teamtailor and Pinpoint fold the employer's host in with `models.tenant_platform_id`); `jobs/history.json`, the ledger and `jobs/output/` use the same key (`known_ids` still hands scrapers raw platform ids). `scripts/migrate_job_ids.py [--dry-run]` converts older data once.
- Scores are attached at match time and written back to the same JSON — there is no separate `matched/` tree; scored postings live at the same path as raw postings.
- Raw and scored postings: `jobs/postings/<YYYY-MM-DD>/<site>/<job_id>.json`
- Generated materials: `jobs/output/<job_id>/cv.html`, `cover_letter.html` (body fragments in the tailor's closed vocabulary, `<!-- Keywords: -->`/`<!-- Tailoring: -->` notes; `compile` wraps them in the template, with the letter's `<<date>>` in the ad's language, and prints them with Chromium; a job prepared with LaTeX keeps its `.tex` and PDFs, unread), and compiled PDFs, plus `facts.json` (`tailoring/facts.py`, run by the tailor itself through the `check_facts` tool, two rounds a prepare run, and again by `prepare` and `revise`; an item still flagged keeps the `reason` the tailor recorded for it, never a TODO, and a company form is no skill: the numbers, years, employers, skills and tools, certifications and degrees not found in `profile/cv.md` or the story bank (`kind`: `number`, `year`, `employer`, `skill`, `certification`, `degree`, and `placeholder` for a `TODO`, a gap of `cv.md`'s, always flagged; skills are read from the CV's Skills/Certifications/Education sections, `i18n` `cv_sections`, and as technical-looking words elsewhere, minus `skill_stop_words`, folded through `jobs/skill_aliases.json` read via `core/skill_aliases.py`, never written; the letter may echo the ad); offline, no model call, reported never blocked). `compile` refuses a body that `tailoring/html_guard.unsafe` names anything in (any tag, class or link outside the allow-list: no script, style, image, SVG, `on*` or non-`https:`/`mailto:`/`#` link): model output never reads or writes other files, except the one photo it asks for: the tailor writes `<<photo>>`, and `compile` (after the guard, like `<<company>>`/`<<title>>`, but the `.html` on disk keeps the token so a recompile passes the guard) copies the profile's photo as `photo.jpg|png` beside it and swaps the token for `<img class="photo">`, or for nothing (no `photo`, a country whose `[cv]` says `photo = "no"`, a template without a `.photo` style); an entry's `<h3>` is written in `role`/`org`/`dates`/`place`/`sep` spans and a stated skill or language level is `<li class="level level-1..5">` with the word kept (#147), `main`/`side` never accepted from the model; `prepare` hands the tailor the job country's `[cv]` block in its prompt (`prepare._cv_conventions_text`; the job's location, else the profile's), and the first sent status copies `photo.*` to `sent/` with the materials and records its sha256. `core/phone.py` (#444) runs the phone server for a data folder under The other door's control (`phone_start` with a Cloudflare quick tunnel or Tailscale, `phone_status`, `phone_stop`, `pair_phone` returning only a QR code: a 24-character, five-minute code never handed out as text; the state in `<home>/.serve/run.json`, cloudflared pinned by digest). `door serve` (#302) answers a paired phone only `serve_policy.PHONE_TOOLS`, with no local paths and no home-network addresses (`serve_policy.refusal`).
- Run records (from `find`, the batch entrypoint): `jobs/runs/<timestamp>.json` per run, with one block per step that ran (`search`, `discover`, `follow`, `collect`, `match`; `null` for the others; each has counts, `elapsed_s`, per-site outcomes where there are sites, and a one-line `summary`), plus a one-line-per-run `jobs/runs/latest.log` summarising the steps run. Read them through `core/runs.py` (`site_entries`). `run follow --dry-run` writes no record.
- Freshness: a **board** (`search`) keeps only postings with `posted_at` after the board's watermark minus a day (`jobs/scrape_state.json`: `{site: {"last_success", "pushback_at"?}}`), never more than `max_age_days` (default 30) back (`src/door/core/freshness.py`). An **employer's feed** (`collect`) has no cutoff and no watermark: a posting is new when `jobs/history.json` has not seen it, whatever its `posted_at` (a date cutoff dropped long-open jobs that get re-advertised as recent). Scrapers receive the cutoff as `since=` (a `datetime` or `None`) and may ignore it; the engine tells them which step runs through `config["_mode"]` (`search` or `collect`; Workable, a board and a feed, reads only its keyword search or only its followed accounts accordingly).
- The example CV (`common._cv_is_example`: `profile/cv.md` byte for byte `profile.example/`'s) is never scored or tailored against: `_match_core` and a `find` that would match raise `ConfigError` (`find` before it reads anything), `_prepare_core` returns `failed`. A sandbox or demo that really runs them holds a changed copy (`scripts/sandbox.py`, `scripts/demo/record.sh`, `app/src/main/demo.ts`).
- Application ledger: `jobs/applications.json` (`core/tracker.py`), `{job_id: {"status", "updated_at", "notes"?, "materials"?, "history": [{"status", "at", "notes"?, "logged_at"?}]}}` (`notes`: why, or how an interview went). `at` is when the event happened (`set_status`'s `at` for a change recorded afterwards, which keeps `logged_at` and is filed in date order); the first sent status (`tracker.is_sent`) copies `jobs/output/<id>/`'s materials to `sent/` and records their sha256 in `materials`, and warns when the ad is not on disk or under 400 characters. One flat list of statuses (`tracker.STATUSES`): `unapplied`, `prepared`, `applied`, `interview:screening|impression|assessment|technical` (one per round), `ghosted`, `rejected`, `offer`, `discarded`; every change is appended to `history`, and `interview_rounds`/`interview_outcomes` read it back as rounds passed, rejected, ghosted, withdrawn or pending; `timeline` is the whole history with each round's result (`jobs show`'s History; `jobs summary` tallies the rounds). `jobs status` picks the job and the status from lists when they are left out; `jobs summary` is the dashboard.
- Market report (`commands/market.py`, the `market` tool): counts the scraped and scored ads of a window (skills, near misses, uncovered titles, repeat companies) and writes `jobs/market/report-<date>.md` under the ledger lock. Skill names go through `jobs/skill_aliases.json` (`{variant: canonical | null}`, `null` = not a skill, dropped); names not in it yet are grouped by one Haiku `claude_cli.ask()` per 200, merged under the lock with existing keys winning (a hand edit is never overwritten); a failed call leaves the names as written and sets `warning`.
- Review watermark: `jobs/last_review.json` (`{"reviewed_at", "seen"}`), stamped by the `mark_reviewed` tool ("I'm done"; no command, and it drops `seen`); "new" means `scraped_at` after it and not in `seen`, the jobs the desktop app opened one by one (`mark_seen`, no command).
- Problem log (#593): `HOME/logs/door.log` (`core/problem_log.py`, rotating, 1 MB × 3), one line per failure: every MCP tool call that raises or answers `{"error"}` (logged in `mcp_server._DoorMCP.call_tool`, the one place, by tool name only, never its arguments; a returned `warning`/`warnings` too, except `set_status`'s, `job_result`'s and `prepare`'s, which is about the user's materials, not a failure), a CLI command's crash (`cli._DoorGroup.invoke`), and each run record's failed or empty sites and unscored ads (`find._write_run_record`). Only `mcp_server.main()` and `door/__main__.py` call `problem_log.setup()`, so tests write no log. The app's main process appends its own lines to the same file (`app/src/main/problem-log.ts`: what the window was refused, a server that died with its stderr, a timeout; `DoorServer`'s `onProblem`). `data report` (`commands/report.py`, tool `report_problem`, Settings → Report a problem → Save logs… through a save dialog in main, `archive-files.reportTarget`) packs the logs, the last 5 run records trimmed to counts, outcomes and errors, doctor's checks and the version and OS into one `.zip`, emails and the data and home folders masked, nothing from `profile/`, no postings, no ledger; saving one stamps `HOME/logs/reported_at` (`core/recurring.stamp_report`).
- CV style build surface (#205, epic #144): `cv style build FILE` (`commands/style.py`) runs `tailoring/style_build.build` in the foreground with `progress=`; the `build_style` tool (a writing tool, `path_scope.check`) does intake (no Chromium to print with, `style_extract.not_pdf` and the verdict, `{"error": words}`, nothing started), copies the PDF to `HOME/.style/source.pdf`, ends a running build's process group and starts `python -m door cv style build <copy>` detached (`core/phone.spawn_detached`, `DOOR_HOME` kept, log `HOME/.style/build.log`), returning `{"started": true}` at once. State `HOME/.style/run.json` (`pid`, `state` building|ready|failed, `started_at`, `result`; `.style/**` LOCAL in `core/stored.py`); `status_summary`'s `style` block (`none`, `building` while the pid lives, `ready` while a candidate waits, `profile/style.next/cv.template.html` (building > ready > failed > none), with the last result's `fonts` and `dropped_icons`, `failed` with `problems`). A build writes only the candidate `profile/style.next/` (DATA in `core/stored.py`), never `profile/style/`, the style in use (#151): in use = the keys `cv_template` and `cover_letter_template` naming `profile/style/`'s two templates (relative to HOME), the default both `null`. `cv style use [like|default|current] [--rerender]` / the `use_style` tool (a writing tool, async, not on the phone; `style._use_core`) moves the candidate into `profile/style/` (`like`, replacing an earlier one, and sets both keys) or ends it (`default` clears the keys only where they point into `profile/style/`, `current` changes nothing in use; a candidate with no built style kept is moved into `profile/style/` unused, else deleted), and with `rerender` (which leaves a candidate alone: the CLI chooses first, then prints) prints the jobs whose ledger status is exactly `prepared` and that have a `cv.html` again through `compile._compile_core`, no model, a job whose compile raises or answers an error listed in `failed`; refuses `like` and `default` without a `profile/config.json`; an interrupted swap (`.style.old`) is put back by `use`, `show` and `status`; returns `{in_use, prepared, rerendered?, failed?}`. The test world's `claude.py` answers the stylist agent through `app/test/world/stylist.py`.
- Progress: cores and scrapers never `print` (stdout is the MCP JSON-RPC stream); they call `report()` (`src/door/core/progress.py`; scrapers import it from `door.scrapers`). `scrape`/`match` (`find`'s two stages)/`find`/`prepare` cores take a keyword-only `progress=` reporter (pass it only when you have one); the CLI renders it on a TTY (a pipe: plain lines), the two long MCP tools (`find_jobs`, `prepare`) are `async` and forward it to `ctx.report_progress`, and `ledger_lock` mirrors the latest event into `jobs/.progress.json` (with the folded `steps` of `pipeline.display.BoardState`, passed on by `status_summary.in_progress`) (removed on release; `status_summary.in_progress`). `tests/core/test_no_print_guard_unit.py` enforces no `print(` under `src/door/`.
- Ledger lock: any core that writes `jobs/` ledgers runs under `door.core.lock.ledger_lock` (or the `_locked` decorator); `find` holds it for the whole run. A new ledger-writing core must take it too.
- Google Drive sync (`core/drive.py` transport, `core/sync.py` logic, `data connect|sync|disconnect` in `commands/archive.py`, tools `connect_drive`/`sync_data`/`disconnect_drive`): the one archive `My Drive/The other door/door-data.tar.gz`. The outermost `ledger_lock` block (not for purposes `export`/`import`/`sync`) calls `lock.pre_acquire_hook` (`sync.on_acquire`: pull) after taking the OS lock and `post_release_hook` (`sync.on_release`: push when `sync.fingerprint` changed) before releasing it, outside `_held_guard`; each pull, push or skipped sync leaves a note (`sync.drain_notes()`) that the CLI group prints on stderr when its command closes (never the MCP server); a failure there is one warning, only `SyncConflict` (both sides changed, names `data sync --keep-local|--keep-drive`) refuses. `CLIENT_ID`/`CLIENT_SECRET` in `drive.py` are the project's Google OAuth client (a desktop-app client, whose secret is not confidential by Google's design); a build with them empty makes `data connect` say "not configured in this build" (`drive.is_configured()`). Only `core/drive.py` names Google's hosts, but for the Chrome for Testing download in `core/chromium_pin.json` (`tests/core/test_no_forbidden_hosts_unit.py`); `tests/conftest.py` turns the hooks off (`enable_sync_hooks` turns them on) and refuses `webbrowser.open`.
- `search_keywords` (optional config key): a broader list of search terms used by all scrapers instead of `role_targets` for their query loops. Falls back to `role_targets` when absent or empty. Ask "expand my search keywords" (or run `/onboard`) to populate it from `role_targets` — see below; from a shell, `init --search-keywords a,b` (or any field flag / `--set KEY=VALUE`) writes one key in place without prompting.
- `topic_terms` (optional config key): the words and phrases that make a job title on topic (`title_fit.topic_terms`/`on_topic`: one of them or a whole keyword; a trailing `*` is a prefix), proposed with the keywords in every ad language, never a bare role noun. Without it, any content word of the keywords counts (synonyms from `i18n/common.toml`).
- `languages` (config key): the job-ad languages to consider, only supported ones (English, Danish, French, Hungarian — a file in `src/door/i18n/lang/`). `scrape`'s language pass (`src/door/matching/language.py`, `py3langid`) drops ads in any other language right after dedup; the candidate's own language skills and levels live in the CV.
- `scrape_workers` (optional config key, default 8, `1` = serial): `_scrape_core` (the engine of `search` and `collect`) scrapes sites concurrently and the per-company feeds (`career_sites`, `successfactors`, `teamtailor`, `recruitee`) fetch entries on different hosts concurrently, at most `PER_PROVIDER` (4) hosts of one provider's domain at once (`src/door/scrapers/_parallel.py`). `PoliteSession` paces per host (one request at a time per host, a pause or the longer `Crawl-delay` before each), so only different hosts overlap. Scrapers produce in worker threads; `_scrape_core`'s own thread does every `jobs/` write and the passes after scraping; every site, The Hub included, runs in the pool (it is plain HTTP; its `window.__NUXT__` is evaluated with the embedded `quickjs` engine). Nothing drives a browser: LinkedIn discovery is plain HTTP too (`requests`, `http_client.USER_AGENT`: a common browser's). `record_error`/`drain_errors(site)` are locked and per site; `progress.scope` is per thread (`current_scope()` hands it to a worker).
- `profile/companies.json` (`src/door/core/companies.py`): the one list of followed employers, `{"version": 1, "companies": [{name, feed: {platform, id} | null, aliases, status: followed|unfollowable|unresolved|dormant, reason, found_via, evidence, first_seen, last_checked, last_relevant}]}`. It replaces the ten per-platform config keys (`greenhouse_boards`, `lever_companies`, `teamtailor_companies`, `workable_companies`, `hr_manager_aliases`, `ashby_companies`, `recruitee_companies`, `pinpoint_companies`, `career_sites`, `successfactors_companies`; now `Site.config_key`, `sites.FEED_SITES`), which `Profile` does not accept (a config that sets one is refused). Scrapers stay stateless and still read those key names: `_scrape_core` (and `doctor`'s probes) merge `companies.feed_config(profile_dir)` into the config they hand them, and `Site.config_key`/`not_configured` work off that. `companies add|remove|list|why` edit and read it; `follow` records into it (`store.record`) the verdict of `commands/companies._classify` for each queued employer as soon as it is known. Only an employer with an on-topic ad is queued (`door.matching.title_fit.on_topic`: one of `topic_terms` or a whole keyword; without them any content word of `search_keywords`/`role_targets`, synonyms from `i18n/common.toml`). `collect` first retires (`store.retire_idle`) the followed employers with no on-topic posting or `min_score` match (`last_relevant`, stamped by `collect` and `match`) for `retire_after_days` (default 90, 0 = never; not for `found_via` manual): status `dormant`, feed kept, not collected; `follow` re-follows a dormant employer seen again with an on-topic ad, as does `companies add`. A followed platform needs no listing in config: `collect` derives its sites from this file. One entry per employer: its other names are `aliases` (formerly `also`, migrated on load; `find`, `is_settled`, `mark_relevant` match name or alias by `name_key`), `record` folds a name found on an already followed feed into them, and `companies merge [A B]` (tool `merge_companies`; with no names it only lists `merge_candidates`, the entries sharing a feed or `name_key`, shared portals excluded) merges the duplicates the user confirms.
- Local jobs only (`src/door/matching/locality.py`, pure): when `location` names a country with an `i18n/country/` file, `career_sites` asks a Workday tenant's job list for the country's jobs (the `locationCountry`/`locationHierarchy1`/`locations` facet of the first answer, via `appliedFacets`), drops sitemap/listing URLs whose path names only another country's place (`foreign_places` in `i18n/common.toml`; remote and place-less stay), and `smartrecruiters` skips detail requests for postings in another country. Every other feed scraper (SuccessFactors, Teamtailor, Greenhouse, Ashby, Lever, Recruitee, Pinpoint, Workable's followed accounts, HR-Manager, Dayforce, and the JSON-LD ads of `career_sites`) runs its postings through `sdk.keep_local` (`locality.location_is_non_local`: the location text names only another country's place, or has a bare uppercase ISO code part, e.g. `, DE`, `, MA`, other than the profile's) and drops those whose parsed `location` is foreign; remote, location-less and multi-location postings with any local part stay, and the profile's `remote` is not honoured. Scrapers report the count with `record_non_local(site, n)` (`drain_non_local`, like `record_error`); `_scrape_core` puts it in the site's result as `non_local` and `collect` sums it into its block and summary. `career_sites` falls back to `applicantLocationRequirements` when an ad has no `jobLocation`.
- The candidates queue, `jobs/candidates.json` (`src/door/core/candidates.py`): `{company_key: {"name", "links", "titles", "sources", "first_seen", "last_seen"}}` (LinkedIn entries also `job_ids`), written atomically under the ledger lock. `search` and `discover` add to it, `follow` removes the entries it recorded, drops those not seen for `max_age_days` and parks LinkedIn employers whose name found no feed (`name_tried`, still `needs_apply_link`) for `discover` to read their job page.
- Academic jobs (#431): the ranks postdoc, assistant and associate professor, professor, adjunkt, lektor and tenure track are one seniority level, `academic` (any rank matches any other); `keywords` proposes institute and department names as topic terms; `euraxess` (board, dk, hu, se, fr and gb) reads a country's EURAXESS list whole (its text search does not narrow it) and keeps offers whose title, research field or teaser is on topic; Aarhus University's Emply list embedded in its page is an `emply_tenants` entry (the page URL); a scheme-less `//delta.hr-manager.net/...?customer=` link names an HR-Manager alias (ITU).
- Job boards: `search` reads every board serving the profile's `location` country (`core/sites.boards_for_location`: the `Site.board` entries whose `countries` include it, plus the worldwide ones); `--boards` narrows one run. Tests read Jobindex alone (`tests/conftest.py` `_one_board`; `country_boards` restores the rule).
- Progress display: `find`'s five lines are `pipeline/display.py` (`render_lines` is a pure function of `BoardState`, which folds the events; `StepBoard` redraws on a TTY, `PlainSteps` prints `[4/5] collect: ... (41m)` per finished step for a pipe or a log file). A step reports itself with `pipeline.running(name)` (`stage="step"`, `site=<step>`) and its work with the `keyword`, `detail`, `postings`, `candidate`, `entry_start`/`entry_end` stages (`scrapers.tracked(entries)` wraps a feed's entry loop); a board at work reports `keyword_search` / `ad_details` (message = the keyword, `done`/`total` = keyword or ad N of M), folded into its item's `activity` and phrased by the app (`screens/run-text.ts`, which also turns the Matches and Prepare spinners' raw messages into words).
- `profile/config.json` is validated against `Profile` (`src/door/core/profile_loader.py`) by every command via `load_config`, with `extra="forbid"`: a new config key must be declared in `Profile` (and in `docs/configuration.md`'s Keys table) or every command will reject configs that set it.
- This project runs on Claude Pro/Max plans only — never an API key. Every LLM call goes through the `claude` CLI in print mode (`claude -p`), which draws from the plan's usage quota; there is no `ANTHROPIC_API_KEY` anywhere in the code or docs. Every `claude` subprocess takes its environment from `door.core.claude_cli.env()`, which sets `CLAUDE_CONFIG_DIR` from the optional `claude_config_dir` config key (which plan pays); a new call site must too — use `claude_cli.ask()` (one question: system prompt, stdin, optional JSON schema and allowed tools, always a `--output-format json` envelope; `src/door/commands/keywords.py`, `titles.py`, `enrich.py`, `gaps.py`, `cv.py`, `market.py`) or `claude_cli.run()` underneath it (`revise` in `src/door/commands/revise.py`, `_run_tailor` in `src/door/commands/prepare.py`), which do; `src/door/matching/scorer.py` and `src/door/matching/language.py` (title translation) keep their own `subprocess.run` for retry, backoff and fallback-model handling but take `claude_cli.env()` too. Every call also names what it is for, a key of `core/usage.FEATURES` (`claude_cli.run`/`ask`'s required `feature=`, or `usage.record(feature, stdout, units=)` beside an own `subprocess.run`), so it is appended to `jobs/usage.jsonl` (weighed by the envelope's `total_cost_usd`; this computer's only, left out of export and Drive sync); `usage.week` (each activity's share of the last 7 days), `usage.room` (the plan's windows and the finds and prepares that fit) and `usage.cost` (#64: what each activity and feature cost at API prices, shown as dollars in `jobs summary`, `status_summary.cost` and the app's Analytics, always called an estimate at API prices, never a bill) read it. `tests/core/test_usage_call_sites_unit.py` fails on a call that names none.

- The app shows an error only when it keeps the user from a mistake or they can fix it themselves; a failure the app retries or the user cannot act on is said nowhere (`docs/design/README.md`, principle 9).
- No backward compatibility while in development: a removed or renamed command, option or
  config key is deleted everywhere (code, tool, docs, tests) as if it never existed. No aliases,
  no "X was renamed / is no longer a setting" messages, no code that drops old keys, no doc
  sentence saying something is gone. A user `profile/config.json` that uses a removed key is
  fixed directly.
  Data written by the last release is the exception (minor versions migrate data, major versions may break it,
  patch versions never change it): it is upgraded on start by the step the
  `data-migrator` agent writes at release time (`src/door/core/migrations.py`: a data version per folder in
  `profile/.data_version` and `jobs/.data_version`, a backup first, a failed step restored, newer data and data of an older major refused; folders are stamped when created, Drive keeps the versions on the file's `appProperties`),
  and every stored file is named in `src/door/core/stored.py` (a test fails for a file a writer stores that it
  does not name); the release gate opens each release's saved data, `tests/data_versions/<X.Y.Z>/`, with `./scripts/run-test.sh --release`; `docs/architecture.md` "Data versions and upgrades"). The HTML templates and fonts are code-owned (`core/templates.py`: a file in `profile/` is the
  user's own override), never copied into `profile/`.

## Code layout rules

- A command lives in `src/door/commands/<name>.py`: its `_<name>_core` (side effects, returns
  a dict, never prints) and the Click command that renders it, registered in `src/door/cli.py`.
  The top-level help is sectioned (`_SECTIONS` in `cli.py`: Set up, Find, Your lists, Your CV, Move); a new top-level command goes into one.
  What several commands share goes in `src/door/commands/_common.py`. `find` is five steps, one
  module each under `src/door/pipeline/` (`search.py`, `discover.py`, `follow.py`, `collect.py`,
  `match.py`; each core returns its block of the run record and never prints) composed by
  `_find_core` in `commands/find.py`. They share the engine `_scrape_core` in `commands/scrape.py`
  (`search` and `collect` call it with their own site list and mode; its `_scrape_passes`
  are run once by the match step) and `_match_core` in `commands/match.py` (scoring).
- Call into another module through the module, never a name imported from it:
  `from door.commands import scrape as scrape_cmd` then `scrape_cmd._scrape_core(...)`, and
  `workspace.JOBS_DIR` (from `door.core import workspace`), read at call time. Tests patch
  the module that defines a name (`monkeypatch.setattr(scrape_cmd, "_scrape_core", ...)`,
  `monkeypatch.setattr(workspace, "JOBS_DIR", tmp)`), and that only reaches every caller
  when callers look the name up on that module.
- The CLI prints a path under the repo relative to it (`common._display_path`: `jobs/output/<id>/cv.pdf`),
  any other path whole; cores and MCP tools return absolute paths (Claude reads the files).
- `src/door/__init__.py` re-exports nothing, so a patch aimed at `door.<name>` fails loudly
  instead of silently patching nothing.

## Running tasks

Stack: **Python 3.12**, dependencies managed with **Poetry only** (`package-mode
= false` — the repo runs in-place, it is not built or installed as a package). The
package lives in `src/door/`; whatever runs it puts `src/` on `PYTHONPATH` — the root
`./door` script (`door.cmd` on Windows), `.mcp.json`'s `env`, pytest's `pythonpath`.
`./door <command>` is the only CLI spelling; `poetry run python -m door` from the
root no longer finds the package.

```bash
poetry install                                 # set up the environment

./door find                # five steps: search the boards, discover employers (LinkedIn), follow
                            # their feeds, collect them, match (filter + score with Haiku), summarise
./door find --skip discover,collect   # leave steps out (options of the group go before a step name)
./door find --boards jobindex,thehub  # search only these boards
# the single steps are hidden from --help (users only see `find`), kept for debugging one step:
./door find follow --dry-run          # what `follow` would record in profile/companies.json
./door find collect --company Trustpilot   # just that followed employer
./door find match          # score what is unscored, list the matches at min_score
./door jobs               # the matches you haven't acted on, best first (--new, --score X)
./door jobs show trustpilot   # one posting in full, named by company/title words (several: pick; none: pick from all); `jobs add URL|TEXT`, `jobs status` (pick a job and a status from lists), `jobs summary` (the dashboard), `jobs prepare trustpilot`
./door cv enrich <url ...>   # propose CV additions from public pages, then add the ones you pick
./door cv gaps --job trustpilot   # skill-gap report + learning plan for a posting (or role names, or --top N)
./door doctor             # prerequisites check (Chromium, claude, MCP entry); --probe adds live site probes
./door doctor --fix       # install Chromium/claude if missing (asks once), check the MCP server
./door data export        # pack profile/ and jobs/ to move computers (`data import` on the other one)
./door companies add Trustpilot   # detect a company's feed and follow it (`--dry-run` shows it first); `companies` lists, `remove`, `why`

./scripts/run-test.sh           # offline tests + coverage + badge (see Testing)
./scripts/run-test.sh --live    # opt-in live smoke tests
```

### MCP server

Every CLI command is also an MCP tool (`src/door/mcp_server.py`), so an LLM client can drive
the pipeline with typed tool calls instead of shelling out and parsing stdout. Each tool
wraps the same `_*_core` function its Click command calls (`src/door/commands/<name>.py`: `_find_core` (the `find_jobs` tool: `step`, `skip`, `boards`, `company`, `dry_run`, ...), `_list_core` (`jobs`),
`_prepare_core`, `_doctor_core`, …) — no behaviour is duplicated between the two
surfaces. Cores return dicts and never print; expected failures come back from a tool as
`{"error": ...}`.

```bash
PYTHONPATH=src poetry run python -m door.mcp_server   # run the server directly (stdio transport)
```

An in-repo `.mcp.json` registers the server for Claude Code (auto-connects when this
repo is opened — see `/mcp`); other MCP clients can point their own config at the same
`command`/`args`. **Adding a CLI command means adding its tool too:** map it in
`CLI_COMMAND_TOOLS` (`src/door/mcp_server.py`); `tests/commands/test_mcp_server.py` fails until the
tool list equals the command list, and until the tool takes every option the command takes
(and vice versa) — `--quiet` excepted; a renaming goes in that test's `_ALIASES`.
A tool with no command is allowed only by name in `CONVERSATION_ONLY_TOOLS` (`revise`,
`mark_reviewed`, `mark_seen`, `compile`, `check_facts`, `preview_matches`: what a user says to Claude, or an agent's or a wizard's plumbing). The CLI is
two levels where it helps: `cv enrich|gaps|titles|stories|style` (`cv stories list|add|remove|draft`, bare = list; `cv style build|show`), `companies list|add|remove|why`, `jobs list|show|add|status|summary|prepare` (bare `jobs` is `jobs list`), `data export|import` and `find search|discover|follow|collect|match` (keys like `"data export"`
in `CLI_COMMAND_TOOLS`; the five `find` steps are one `find_jobs` tool whose `step` parameter picks the subcommand, with the group's own options like `skip` beside it); `doctor --fix` is the `setup` tool. Skills and agents call these tools — no `.claude/` file
runs `./door`. See
`docs/architecture.md`'s "Two modes, one core" section for the full CLI / MCP /
skills-and-agents model; the tool table users read is `docs/manual-claude.md`.

### Review sessions (default behaviour of a conversation in this repo)

The user runs door by hand when they sit down; a conversation here fetches what's new
and helps decide. Unless the user asks for something else:

1. Start with `status_summary` — its `since_last_review` block says how many runs
   happened, how many new matches cleared `min_score`, and which sites failed. Mention
   failures briefly; don't try to fix them unasked. If there has been no run since the
   last review (or the user asks for fresh jobs), offer to call `find_jobs` — it scrapes only
   postings published since each site's last scrape, then scores them (minutes).
   Its `pass_rates_by_score.reading` being `"near_min_lower"` means matches near `min_score` led to an interview clearly less often: mention that raising `min_score` may help.
   Its `plan` block says how full the Claude plan is: mention it only when it has a `warning`
   or little room; answer "can I prepare three more?" or "why did I hit my limit?" from it
   (`room`, `week`), saying it is an estimate as of `as_of`. Its `cost` block answers "what did
   that cost?": dollars at API prices per activity, an estimate and not a bill.
   Its `no_answer` block counts applications with no answer in `days` days (`tracker.NO_ANSWER_DAYS`):
   when it is above 0, call `list_matches(ongoing=True)` and name those rows (step 4).
   Its `style` block `state` `ready` means a style built from the user's CV waits: say so and call `show_style` in the same turn, not offering it first, `Read` the first CV
   page of `styles.default.cv` and of `styles.like.cv` and give both paths with a sentence on the difference (and, when
   `two_column` is true for one, "Some application systems read two-column CVs less well."), then ask with
   `AskUserQuestion`, neither option recommended, "Keep The other door's" (or "Use The other door's" when `in_use` is
   `like`) then "Use the style of my CV" (plus "Keep my current style" only when `in_use` is `like` and there is a
   `candidate`), and call `use_style` with the pick ("Keep/Use The other door's" is `default`, "Use the style of my CV"
   `like`, "Keep my current style" `current`); when the pick was not `current` and its answer has `prepared` above 0,
   offer `rerender`. Any other `state` (`building`, `failed`, `none`): unasked, do not mention the CV style at all, not
   even that a build is running or failed (it is not one of the failures above); asked ("is my style ready?"), say in
   one line that it is still being built, that the build failed (its `problems`), or that none was built. "Use my CV's style" at any time: with a candidate the same pick, otherwise ask for the PDF (inside the data
   folder) and call `build_style` with it, its error in one line.
2. Then `list_matches(new_only=True)` (or plain `list_matches` if nothing is new, or the
   user wants everything). Present postings by title and company (with `title_en` next to
   a title in another language), never with numbers. The user names a job in their own
   words ("the Trustpilot one"); pass the `id` from the list you showed, or their words —
   every tool that takes a `job_id` accepts words from the company and title, and returns
   `candidates` when several jobs match: ask which with AskUserQuestion. Never ask the user
   for a job id or a path.
3. Don't call `find_jobs` (it re-scrapes and re-scores) without the user's go-ahead.
   If a tool says
   "a run is in progress", tell the user and wait — don't retry in a loop.
4. A row with `no_answer` (from `list_matches(ongoing=True)`, or `show`): say it in words ("no answer in
   `no_answer_days` days"), by title and company, and offer to mark it ghosted; call `set_status` `ghosted` only when they say so
   (their words in `notes`).
   "show the Trustpilot one" → `show`; "not this one" → `set_status` `discarded` (their reason in `notes`); "prepare it" →
   `prepare` ("prepare the best one": no `job_id`), then `show` and summarise its `materials` (keywords, what was tailored, page counts, letter length) with
   the PDF paths; `materials.unsupported` lists numbers, years, employers, skills, certifications and degrees in the CV or letter that `cv.md` and the story bank do not back, each with its context line: tell the user and offer `revise` to remove or fix them (never edit the `.html`); `[]` is clean, `null` means not checked (no `cv.md`), and a sent status's `warning` may list them too; `materials.readability` (also `prepare`'s own `readability` and `warning`, after it retried the tailor once for a missing name, heading or keyword, or text of the CV cut off the page) lists what an ATS would not read back from the PDFs (`tailoring/readability.py`, pypdfium2 text: name, headings on their own line and in order, each column of a two-column CV in its own order and a side heading allowed on a shared line, keywords, garbled or empty text, words of the CV missing from its PDF (`overflow`) and a nearly empty last page of a two-column CV (`sparse`, reported only); `[{file, kind, detail}]`, `[]` clean, `null` not checked): tell the user and offer `revise`; "tighten …" → `revise` (then `show` again); "undo" → `revise(undo=True)`.
   Change a prepared `.html` only through `revise`, never with Write/Edit: `revise` recompiles
   and re-renders, so the PDF never goes stale (there is no compile command for the user);
   "applied" → `set_status`; an interview → `set_status` `interview:<kind>` (screening,
   impression, assessment, technical), one call per round (if the user doesn't say which kind, ask
   with AskUserQuestion, the four as options; "rejected" ends the last round); never ask the user
   to type a status, a kind or a job id from memory — offer the list; "here's a link" → `import_posting` with only the `url` (it fetches the page and Haiku reads title and company; if that errors, ask for the text); "here's an ad I found" → `import_posting` with the pasted
   text (ask for title/company if the ad doesn't make them clear); either way it is scored at once —
   give its score and reason and let the user decide (`prepare`, `discarded`, …).
5. When the user says they are done with the review (after matches were listed), call `mark_reviewed`; not at the end of a skill or any other task.

"Expand my search keywords": call the `keywords` tool (it proposes from the profile's
`role_targets`; the rules live in `src/door/commands/keywords.py`, the same call as
`init`'s reading step in a shell), show the keywords and the `topic_terms`, confirm them (use all / drop some / add some), then
save the confirmed lists with `init_profile` passing only `search_keywords` and `topic_terms` (or
`keywords(save=True)` when they take them all).

"How does the market look?": call `market` and present its report. "Make a plan for the top 3 gaps" →
`skill_gaps` with those skills as targets; "add those titles" → confirm, then `init_profile` with
`search_keywords` set to the current list plus the confirmed titles (it replaces the list); "follow X"
for an unfollowed repeat employer → `add_company`.

"Run doctor" means the `doctor` tool. `/doctor` is Claude Code's own command (it checks
Claude Code's install), not The other door's.

## Testing

This project is developed **test-first (TDD)**. The cycle is non-negotiable for
new behaviour:

1. **Red** — write a failing test that pins the behaviour you want.
2. **Green** — write the minimum code to make it pass.
3. **Refactor** — clean up with the test as a safety net.

Practical rules:

- No new scraper logic (parsing, mapping, pagination, dedup) lands without a
  test written first. Bug fixes start with a failing test that reproduces the bug.
- Keep parsing **pure and separable** from network I/O so it can be tested
  without a live site — this is the main reason the helpers in each scraper
  (`_location_text`, `_parse_stash`, …) are standalone functions.
- Tests must be deterministic and offline by default. Anything that touches the
  network goes behind the `live` marker.
- Test behaviour, not decisions: no test that only asserts an option, command or
  field is gone, that `--help` lists exactly these options, or that an old name is
  rejected. When removing or renaming, update or delete the tests that break.
- While iterating on a change with the user (a live UI session), do not run the
  tests after each edit; run them once, before the PR.

### Layout

`tests/` mirrors the package (see `tests/README.md`): `scrapers/` holds each
scraper's tests next to its saved `fixtures/<site>/`; `commands/` has one
`test_<command>_cli.py` per CLI command (shared `cli_env` in `commands/conftest.py`,
helpers in `tests/cli_utils.py`); then `core/`, `matching/`, `tailoring/`. Use `tests/paths.py` (`REPO_ROOT`, `TESTS_DIR`,
`GOLDEN_DIR`) instead of `Path(__file__).parent...`.

### Three layers

| Layer | Scope | Network | Where |
|-------|-------|---------|-------|
| **Unit** | Pure helpers + `models.py` in isolation (`make_job_id`, `_location_text`, `_parse_date`, `_area_for_profile`, `_country_code`, date/URL fallbacks). | No | `tests/<area>/test_*_unit.py`, `tests/core/test_models.py` |
| **Fixture** | The whole `scrape(config)` path — pagination, dedup, raw→`JobPosting` mapping — with HTTP mocked (`responses`) from saved real payloads. | No (mocked) | `tests/scrapers/test_*_scrape.py` + `fixtures/<site>/` beside them |
| **Smoke** | Probe-sized checks against the *live* site, one test per mode in its `test_<site>_live.py` (#19): `listing` (page 1 through `probe`), `page2`, `details` (two ad pages; `NO_PAGE2`/`NO_DETAILS` say why a site has none), `zero_hits` (a board), `detection` (a feed platform's careers page, `tests/live_employers.py`), `employers` (a discovery source), each under a request ceiling (`live_utils.probe_sized`) and the field contract over a sample (`live_utils.assert_contract`: title, company not the site's own name, url, a local location for a country board, a plausible `posted_at`, a description past a floor and not boilerplate); a failure names the site and the mode (`reed [details]: ...`), and `tests/scrapers/test_live_modes_unit.py` fails offline until each mode that applies has its test. Catches silent breakage when a site changes. The weekly CI run leaves out the discovery sources' live tests (`tests/scrapers/discovery/`), which run locally. Countries and ad languages are checked offline on saved real ads (#19: `tests/i18n/test_country_corpus.py`, `test_language_corpus.py` read `tests/i18n/corpus/`, which `scripts/refresh_corpus.py` writes from the rows in `tests/live_matrix.py`, the only part online; a row required per data file by `tests/i18n/test_live_matrix_unit.py`), and `scripts/smoke_report.py` lists boards, employer feeds and the matcher's golden cases separately on `docs/badges/live-smoke.md` (a list a run did not test keeps its last result: CI has no Claude plan and skips the golden set), with one README badge each (`docs/badges/live-<dimension>.svg`, "passed/total", green when all passed, red when one changed, orange otherwise). Three verdicts (#19, `tests/live_utils.py`): passed, changed (a failure: the only one that opens the failure issue) and not reached (a refusal or an unreachable host: `not_reached_if_refused(site, errors)` or `not_reached(site, why)` skip with `not reached:`, locally and in CI; the page counts the runs in a row, and 3 open an issue of their own). | Yes | `tests/**/test_*_live.py`, marked `@pytest.mark.live` |

Note: `scrape()` swallows network/parse errors (prints and returns `[]`) so a
single bad request never crashes a run — but it also calls `record_error()`
(`src/door/scrapers/__init__.py`) alongside every such print, so `_scrape_core`
can tell a genuinely quiet day apart from a broken scraper after the fact: a
site with `count == 0` and no recorded errors is `outcome: "ok"`; a site with
`count == 0` and recorded errors is `outcome: "failed"`, with the captured
messages under `"errors"` (a site with `count > 0` always stays `"ok"`, even
if some requests also failed — partial success isn't downgraded). A site that
returned not a single record — no errors, but nothing new, known or too old
either, and no recognised zero-hit results page (`sdk.record_answered`: a scraper that read the site's own "no hits" answer, which is a quiet day, `ok`) — is `outcome: "empty"` with a `"warning"`: a flag (the site may have
changed), not a failure — exit code unchanged, watermark not moved, and listed
in `status_summary`'s `site_failures`. A per-company feed platform that no followed
employer uses is never fetched (`collect` does not even list it unless named): `outcome: "not_configured"`, a quiet skip; a site resting
after pushback (`Site.cooldown_hours`) is skipped as `outcome: "resting"` with its `until`, also a quiet
skip. `find`
exits non-zero (2) if any site comes back `"failed"` or `"error"`. The smoke layer is
still what catches a *systemic* site change offline testing can't see — keep
it asserting ≥1 result.

### Commands

```bash
poetry install   # runtime + dev deps (pytest, pytest-cov, pytest-xdist, responses, genbadge)

./scripts/run-test.sh           # offline suite + coverage + regenerate badge
./scripts/run-test.sh --live    # opt-in smoke tests against real sites
./scripts/run-test.sh --model   # the tests run by the real model on your plan, before a release: the skills (/onboard, /expand), a review session, the CV style rebuild (every style corpus CV)
./scripts/run-test.sh --cli-journeys  # the real ./door in the app's test world (init, find, jobs show/prepare/status; needs Node and npm ci in app/; CI: cli-journeys.yml, Linux and Windows)
./scripts/run-test.sh --app     # the desktop app's tests as CI runs them (typecheck, unit, e2e, every journey, phone)
./scripts/run-test.sh --release # before a release: offline suite, app with every journey, CLI journeys, real-model tests, and the
                                # install test when DOOR_INSTALLER names an installer; a PASS/FAIL line each
```

The real-model tests (`tests/model/`, marker `model`, never in CI) run a Claude Code skill with the real
model through the Agent SDK (`claude-agent-sdk`, on the plan `claude` is signed in to, the API key cleared)
against the app's test world (`app/test/world/make-world.ts`: `boot.py`'s server, the stand-in `claude.py`
for the tools' own model calls), with a small model playing the persona (`tests/model/skill_run.py`, which
also runs one skill by hand and writes its transcript). They check behaviour only: the tools and their order,
what was written and when. `tests/model/test_skill_contract_unit.py` (offline) checks that every tool a skill
or agent names exists, with the parameters it passes. `tests/model/test_style_rebuild.py` (#238) runs the
CV style rebuild with the real stylist on every style corpus CV and its edges; it needs a signed-in `claude` and the pinned Chromium.

The offline suite runs in parallel (`pytest -n auto`, pytest-xdist, in `run-test.sh` and CI;
`-n 0` runs it serially, and live runs stay serial), so a test must not share a fixed path,
port or global with another: use `tmp_path` and the `tests/conftest.py` fixtures.

### Coverage badge

Coverage is reported with `pytest-cov`/`coverage` (config in `pyproject.toml`)
and rendered into a badge **entirely locally** with `genbadge` — no Codecov or
other external service. The badge SVG lives at `docs/badges/coverage.svg` and is
committed so it shows in the README. Regenerate it by running `./scripts/run-test.sh`
after changing tests; `coverage.xml` and `.coverage` are gitignored, only the
SVG is tracked.

## Docs maintenance

README is only the get-started path plus links; reference material lives in `docs/`. When
an implementation adds user-facing behaviour, update the matching doc: a CLI command →
`docs/manual-cli.md` and `docs/manual-claude.md`; a config key → `docs/configuration.md`; a
scraper → `docs/job-sites.md` (and `docs/architecture.md`'s Scrapers table); a skill →
`docs/skills.md`; a change to how data is stored → `docs/how-it-works.md` or
`docs/architecture.md`. Touch README only when the get-started steps change. Do not update
docs for internal refactors, test additions, or changes with no user-visible effect.

## Claude agents and skills

Custom agent definitions live in `.claude/agents/` — each is a markdown file with a YAML frontmatter block describing the agent's role and tools.

Custom skill definitions live in `.claude/skills/` — each is a markdown file that Claude Code can invoke via `/skill-name`.
